# 康康健健 HealthDoc 数据库设计说明

> 文档状态：融合历史模型演进、第七轮资金闭环与第八轮搜索读取边界的 SQLite/openGauss 设计说明。当前物理基线仍为 schema v13，更新于 2026-08-07。

第八轮没有新增表、字段、索引或迁移，也不修正现有套餐数据。目录召回只读取既有 `organizations`、`institutions`、`packages`、`package_versions`、健康领域及关联关系；查询意图、推荐分数、搜索历史与短期缓存均不落库，线上数据库按普通代码发布原样保留。

schema v10 奠定预约资料副本、通知、规范附件和指标方向结果；schema v11 增加 Agent/OAuth；schema v12 加入实名认证、关联账号、报告复核和平台治理。当前 schema v13 新增付款订单、逐人资金明细、退款案件、财务交易与不可变账本；SQLite 使用原子副本升级，openGauss 由 `20260804_schema_v13` 保留式增量迁移。

## schema v13 资金模型

| 表 | 关键职责 |
|---|---|
| `payment_orders` | 付款人、预约组、总额、15 分钟到期时间和 `pending/paid/partially_refunded/refunded/expired` 状态 |
| `payment_order_items` | 每位受检者的金额、2.5% 服务费、机构净额、结算日、退款期限和资金状态 |
| `refund_cases` | 投诉的一对一退款案件、裁决、责任说明、72 小时期和退款完成时间 |
| `finance_transactions` | 带幂等键的付款、结算、退款业务交易 |
| `finance_ledger_entries` | 平台托管、平台服务费、机构可用余额的不可变正负分录 |

`institutions.operations_suspended_at/reason` 独立表达运营暂停，不复用账号或机构的 `is_active`。旧 `fulfilled` 预约按预约时套餐价格回填为历史已付款、已结算明细；其他旧预约不伪造在线付款事实。

## 1. 设计目标

数据库服务于“用户健康旅程 + 机构履约服务 + 平台治理”，而不是把数据表直接暴露为产品模块：

- 用户从健康总览记录自主测量，在健康时间线查看自主记录与体检结果；
- 体检套餐是可版本化的服务产品，包含适用人群和健康领域；
- 一次同行体检安排可包含多名参与者，并保留完整状态事件；
- 机构按到检、录入、复核、归档的任务流生产健康档案；
- 满额候补、空位通知、文本结论和附件均是正式业务对象。
- 机构主体与分院分离：报告归档后可在同主体内跨院只读，运营数据仍归具体分院。

本地数据库位于 `backend/instance/health_system.db`，使用 `PRAGMA user_version=13`。生产环境通过 `DATABASE_URL` 连接 openGauss，并以 Alembic 修订 `20260804_schema_v13` 标记结构。

### 1.1 从 1.0 到 3.0 的数据模型演进

| 产品阶段 | 数据建模重点 | 结构结果 |
|---|---|---|
| 1.0 | 账号、机构、套餐、单人预约和基础健康记录 | 建立核心实体与角色外键，支撑最小业务闭环 |
| 2.0 | 自主测量、机构报告状态机、亲友授权和时间线 | schema v6 将个人记录与机构报告分开，报告形成草稿、锁定、归档的生命周期 |
| 3.0 第一阶段 | 健康领域、套餐版本、多人预约、容量候补、通知、文本结论和附件 | schema v7 将服务产品、历史快照、可靠通知和图文健康档案正式建模 |
| 3.0 分院阶段 | 机构主体、分院归属和跨院归档访问审计 | schema v8 新增 `organizations` 与 `report_access_logs`，报告同主体跨院只读，运营数据继续按分院隔离 |

迁移始终保留账号身份和已发生的历史事实。新结构通过迁移脚本显式升级，不能依靠 `db.create_all()` 猜测修改已有数据库。

## 2. 业务域与数据表

| 业务域 | 主要表 | 作用 |
|---|---|---|
| 账号与关系 | `users`、`friend_relations`、`delegation_session_audits`、`delegated_action_audits` | 三角色账号、一次性身份确认、双向关联、真实操作者/有效账号链与敏感操作审计 |
| 机构服务 | `organizations`、`institutions`、`institution_images`、`comments`、`comment_sanctions`、`comment_appeals` | 机构主体、分院、唯一机构账号、相册、评论处罚与申诉 |
| 健康领域 | `indicator_categories`、`indicator_dicts`、`health_domains`、`indicator_domain_links` | 标准指标、可自主测量范围及领域归属 |
| 套餐产品 | `packages`、`package_versions`、`package_version_domains`、`package_change_requests` | 套餐身份、历史版本、适用领域和审核记录 |
| 预约服务 | `booking_groups`、`appointments`、`appointment_events`、`appointment_capacity_slots`、`booking_participant_tokens`、`booking_participant_authorizations` | 三类参与人、一次性令牌、授权证据、进度事件与可约名额 |
| 候补通知 | `waitlist_subscriptions`、`waitlist_subscription_participants`、`availability_notification_events`、`notification_outbox`、`notification_deliveries` | 满额候补、同行参与者、通知事实、可靠投递与尝试记录 |
| 健康档案 | `self_measurements`、`institution_reports`、`report_indicators`、`report_text_results`、`report_assets`、`report_asset_annotations`、`report_access_logs` | 自主测量、机构归档、数值指标、文本结论、附件、标注与跨院访问审计 |
| 投诉与画像 | `appointment_complaints`、`complaint_messages`、`complaint_events`、`institution_audience_insight_cache` | 预约级投诉、追加式沟通/事件、匿名聚合画像与 24 小时 AI 缓存 |

AI 会话、验证码和 JWT 不进入业务数据库；AI 只读取获准的健康事实，不形成新的医疗档案。

## 3. 关键关系

```text
organization ── institution(branch) ── package ── package_version ── health_domain
      │             │
      │             └── booking_group ── appointment ── appointment_event
      │                                      │
      └──────────────── institution_report ──┼── report_indicator
                                             ├── report_text_result
                                             └── report_asset

user ── self_measurement
user ── appointment
user ── friend_relation（双向关联）── delegation_session_audit
booking_group ── appointment ── booking_participant_authorization
appointment ── appointment_complaint ── complaint_message / complaint_event
```

- `packages` 表示可持续识别的套餐产品，`package_versions` 保存每次获批后的名称、价格、说明、适用人群和生效事实。
- 预约保存所选套餐版本与展示快照，后续调价或下架不会改写历史安排。
- `booking_groups` 代表一次同行安排，`appointments` 代表其中每位受检者的服务记录。
- `appointment_events` 记录创建、取消、到检、归档等节点，时间线直接读取业务事件。
- 归档报告可同时包含结构化指标、文本结论与附件，不再把现实报告简化为单一数值表。
- 报告始终记录源分院；同机构兄弟分院只能读取 `published` 报告，详情和附件访问分别写入 `report_access_logs`。

## 4. 核心完整性规则

### 4.1 账号与权限

- `role` 仅允许 `user/institution_admin/admin`。
- 普通用户必须有唯一健康身份码且不能绑定分院；一个分院至多绑定一个有效机构账号；管理员两者均为空。
- `identity_completed_at` 是实名认证完成的物理事实列；`allow_health_id_proxy_booking` 默认开启，用户可关闭新健康码代预约。
- 分院有业务数据后不得随意迁移机构主体；停用机构主体或分院只阻止新业务，不删除历史报告。
- 密码仅保存 bcrypt 哈希；停用账号不能登录、刷新令牌或继续受保护操作。
- 亲友接受后形成双向关联；受控会话保存 actor、subject、完整链和安全版本，最多三层且禁止循环。健康码临时参与人不会形成关联。

### 4.2 套餐与预约

- 套餐业务身份与版本内容分离，预约引用明确版本并保存必要历史快照。
- 机构提交套餐变更，管理员审核通过后才产生或启用正式版本。
- 同行安排最多五名参与者，类型固定为 `self/linked_account/health_code_token`；服务端统一复核身份、令牌、日期、套餐和容量。
- `appointment_capacity_slots` 保存机构日期名额，候补订阅只在满额场景创建。
- 取消或失效释放名额，通知事件和 outbox 保证空位提醒可追踪、可重试且不重复发送。

### 4.3 健康档案

- 自主测量仅允许指标字典中开放的指标，同一指标同一天可以多次记录。
- 机构报告必须来自可履约预约；受检者、日期、机构和套餐版本来自预约事实。`pending_review` 前记录上传医生，`published` 前记录复核医生。
- 报告归档后内容不可修改或撤下；数值指标、文本结论和附件随档案一起保留。
- 同一天同一指标存在机构结果时，趋势优先使用机构值；否则采用当天最后一次自主测量。
- 趋势、时间线、体检数据和健康 AI 只读取当前有效账号的权限过滤事实；关联亲友需先切换账号。
- “体检数据”列表只查询机构归档报告；个人测量继续由总览、时间线和趋势读模型读取。

## 5. 快照与 JSON 的使用边界

以下字段是发生当时的业务事实，而非重复缓存：

- 预约中的受检者、套餐版本、名称、价格和联系方式快照；
- 报告中的受检者与创建者展示快照；
- 套餐审核的变更前后内容；
- 报告识别诊断、通知载荷和外部投递结果。

实体关系、指标明细、套餐领域和同行参与者仍使用关系表表达。JSON 只保存审计快照或外部交互载荷，不替代可查询的业务关系。

## 6. 事务与并发

- 分院、唯一机构账号和凭据邮件 Outbox 在同一事务创建；邮件失败不回滚账号。
- 同行体检安排先校验全部参与者与名额，再整体提交；任一参与者不满足条件时全部回滚。
- 机构容量变更、预约创建/取消、候补触发在锁定的日期容量记录上处理。
- 报告复核发布与预约履约、事件、通知、锁档和临时文件清理同步提交，避免部分发布。
- 套餐审核通过与正式版本生效同步提交。
- 通知采用 outbox：业务事务只写待投递事件，发送失败不回滚已成立的预约事实。


## 8. 当前验收快照

当前 v13 快照固定保留 5 个机构主体、15 个分院、现有有效套餐和完整资金状态；启用可登录账号为 23 个（2 管理员、15 机构、6 普通用户）。

数据同时覆盖身份、关联、参与人、报告、投诉治理与付款/结算/退款状态。具体账号、资金、媒体、完整性和外键结果由只读 `validate_v13_demo.py` 输出，并以《测试报告》的最终门禁记录为准。

## schema v11 历史增量

schema v11 在 v10 业务表上只做加法，新增 Agent 线程、运行、脱敏工具事件、待确认 Action、幂等执行、人工工单及 OAuth 客户端/授权码/访问令牌/刷新令牌表。会话和 Action 参数使用 AES-GCM 密文列，OAuth token 只保存 SHA-256 摘要。预约业务表不复制；Agent 确认调用原预约领域入口，因此容量、状态、通知和历史快照仍只有一个事实来源。

schema v11 当时由 `upgrade_local_database.py` 与 `migrate_schema_v11.py` 交付；该说明仅用于理解迁移链。

## schema v12 历史增量

- `users` 新增 `identity_completed_at`、`allow_health_id_proxy_booking`、`booking_authorization_version`、`must_change_initial_password`，沿用 `token_version`；开发期短暂出现的 `profile_completed_at` 会被事务归一为唯一物理列 `identity_completed_at`。
- 分院机构账号绑定建立唯一约束；重复账号按用户 ID 最小者保留，其余停用、解绑并递增安全版本。
- 旧任一有效亲友/预约授权迁为双向 `friend_relations`；合并正反向重复行前，`booking_participant_authorizations` 与 `waitlist_subscription_participants` 中存在的 `friend_relation_id` 必须先重映射到保留行，避免 `ON DELETE SET NULL` 丢失历史关联证据；运行时不再以旧独立预约授权字段决定访问。
- 新增关联会话审计、参与人令牌/授权、投诉消息/事件、评论处罚/申诉、机构画像缓存；报告新增上传/复核医生和时间。
- v12 当时的迁移规则保留在本节作为历史审计；当前 v13 迁移入口见本文前部资金模型与部署文档。

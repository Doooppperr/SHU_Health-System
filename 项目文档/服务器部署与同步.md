# 康康健健 HealthDoc 服务器部署与同步

> 文档状态：覆盖历史发布与 schema v13 的部署、迁移、冷备份和回滚方案，更新于 2026-08-07。第八轮采用保留数据的普通代码发布；既有 release 记录仍是历史事实。

第八轮必须仅执行 `scripts/deploy-server.ps1` 的普通发布，不传 `SyncDemoDatabase`、`SyncDemoMedia` 或 `SyncMailSettings`。发布仍会建立冷备并运行现有 schema v13 幂等迁移门禁，但不得以本地 SQLite、媒体、SMTP 或密钥覆盖服务器状态。发布后须核对 `/api/health`、`/release.json`、API/通知/Apache 服务、error 日志和公开智能搜索，服务器 SHA 必须与 GitHub `main` 一致。

当前发布工具支持 schema v13 保留式增量发布，以及显式选择的验收数据库全量替换。两种模式都验证干净 `main == origin/main`，把同一 Git SHA 写入发布包、前端构建和 API；每个 release 先建立独立虚拟环境，停止 API、通知、MCP 与 Agent timer，冷备份数据库、上传、环境、systemd 和旧 release，再执行 `migrate_schema_v13.py`。公开提交点之前任一步失败时整体恢复；提交点之后禁止冷回滚已被公开请求写入的资金事实。

## 1. 服务器拓扑

- 公网入口：Apache 监听 80，前端构建文件位于 `/var/www/html/`。
- API：Apache 将 `/api` 与 `/uploads` 反向代理到 `127.0.0.1:5050`。
- 后端：`healthdoc.service` 以非登录系统用户 `healthdoc` 运行，代码入口为 `/opt/healthdoc/current/backend`；解释器和命令来自 `/opt/healthdoc/current/venv`，不再由所有 release 共用一个可变虚拟环境。
- 邮件：`healthdoc-notifications.service` 以同一受限用户常驻运行，每 5 秒条件领取 Outbox；发送前把事件载荷转换为连续中文正文，不暴露 JSON 内部字段；生产单元带 `--start-gate-file /var/lib/healthdoc/notification-worker.enabled`，文件不存在时只等待、不领取 Outbox。每个 `sending` 领取都有 300 秒租约，SIGTERM 会等待当前投递结果落库后退出，systemd `TimeoutStopSec=330` 覆盖该租约；过期租约自动重试，SMTP 固有采用 at-least-once 语义。
- 数据库：openGauss 容器 `healthdoc-gaussdb`，仅绑定 `127.0.0.1:5432`，数据持久化到 `/var/lib/healthdoc/opengauss`。
- 上传文件：`/var/lib/healthdoc/uploads`。
- RAG 运行目录：`/var/lib/healthdoc/rag`，由 `healthdoc` 用户持有，保存 Qdrant Local、嵌入模型和缓存。
- 生产环境变量：`/etc/healthdoc/healthdoc.env`，权限为 root-only，不进入 Git。

生产必须提供至少 32 字符的独立高熵 `ACCOUNT_CREDENTIAL_ENCRYPTION_KEY`。该密钥只用于机构初始账密 Outbox 的临时 AES-GCM 密文，不与 `AGENT_DATA_ENCRYPTION_KEY`、JWT 或 SMTP 凭据复用。发布脚本在缺失时生成，但日常发布不会轮换；冷备份和回滚必须恢复原环境文件，否则尚未发送的凭据无法解密。任何真实值都不得写入仓库、发布参数或日志。

本地开发使用 `backend/instance/health_system.db`。服务器通过 `DATABASE_URL` 使用 openGauss。普通代码发布不上传 SQLite；`-SyncDemoMedia` 只同步清单限定的 34 个验收素材，不覆盖数据库；只有显式指定 `-SyncDemoDatabase` 时才生成一致性临时快照并全量同步。

## 2. 两种发布模式

本地发布入口要求 PowerShell 7 或更高版本，避免 Windows PowerShell 5.1 改写传给 Python 的多行快照校验参数。

普通代码发布：

```powershell
.\scripts\deploy-server.ps1
```

它保留服务器现有数据库和上传目录，更新时间戳代码版本与前端构建，并从仓库批准清单同步公共 RAG 知识；RAG 同步失败时保留原环境和当前版本。

仅刷新报告验收素材（保留线上业务库）：

```powershell
.\scripts\deploy-server.ps1 -SyncDemoMedia
```

该模式先完整备份 openGauss 和上传目录，只替换 `institutions/demo-v8` 与 `health-assets/demo-v8`、`health-assets/demo-v10` 三个精确目录，执行数量、标准槽位、尺寸、无 EXIF 和 SHA-256 校验，并更新已有报告附件的标题、槽位、机构批注与文件元数据。较早完成 v10 迁移的库会先幂等补齐缺失的标准附件类型配置；账号、预约、报告、评论和套餐记录不会被导入、删除或覆盖。

验收数据库与匹配附件全量同步，并保留服务器既有 SMTP/密钥：

```powershell
.\scripts\deploy-server.ps1 -SyncDemoDatabase -SyncDemoMedia
```

该模式明确清空 openGauss 应用表并导入经 v13 强校验的 SQLite 快照，只适用于用户已确认可覆盖的验收环境。脚本记录服务与通知门闩原状态、停止全部写服务后备份 `/var/lib/healthdoc/opengauss`、上传目录（或“原目录不存在”标记）、旧环境、旧 Apache 配置和当前 release；导入逐表核对，并只接受清单登记的 34 个媒体。公开提交点前的数据库、附件、RAG、SHA/schema 或服务候选检查失败会整体恢复；公开提交点后只允许只读核验和人工修复/重新发布，不再自动恢复旧数据。

`-SyncMailSettings` 从被 Git 忽略的本地 `backend/.env` 读取 SMTP 白名单字段，以 UTF-8/LF 临时文件经 SSH 写入 `/etc/healthdoc/healthdoc.env` 后立即删除；服务器导入端也会防御性清除 Windows 回车。它要求 SMTP 主机、端口、用户名、授权码和发件人完整，且 `NOTIFICATION_EMAIL_DRY_RUN=0`；授权码不会出现在 Git、发布命令或文档中。

`upgrade_local_database.py` 只用于 SQLite 旧库升级；跨数据库全量同步使用 `migrate_sqlite_to_gaussdb.py --replace`。

`reset_v13_demo_data.py` 只用于本地验收库，不属于服务器发布或生产迁移流程，任何生产环境都不得执行；旧入口仅保留为历史命令兼容包装。

## 3. schema v13 生产迁移验收项

### 数据结构

- `users` 包含健康身份、个人资料和 `is_active` 字段，并满足角色/机构/健康身份约束；
- 每个分院至多一个有效机构账号；历史重复账号停用并解绑；
- 存在健康领域、指标领域关联、套餐版本、套餐版本领域关联；
- 存在同行安排、参与者预约、预约事件、日期容量、候补订阅、空位通知与 outbox；
- 存在自主测量、机构归档、数值指标、文本结果和报告附件；
- 指标字典包含自主测量开放标志，健康时间线支持体检/自主记录投影；
- 存在实名认证、双向关联/关联链审计、参与人令牌/授权、投诉、评论处罚/申诉和机构画像缓存结构；
- 存在付款订单、逐人资金明细、退款案件、交易和不可变账本表，机构运营暂停字段独立存在；
- Alembic 修订为 `20260804_schema_v13`，健康检查返回整数 `schema_version=13`；
- 活动报告的唯一性规则正确；
- 报告创建账号删除时外键置空、快照保留；
- 普通用户删除时健康数据按设计级联。
- 应用启动通过 SQLAlchemy Inspector 校验 openGauss 表、列和命名约束，不执行 SQLite 专属的 `sqlite_master` 查询。

### 数据与文件

- 系统管理员账号和密码哈希正确；
- 机构、套餐版本、领域关联、相册与评论数据处置符合迁移方案；
- 上传目录只保留数据库引用的机构图片、报告附件和必要临时文件；
- 公共 `/uploads/reports/...` 返回 404；
- 报告复核发布后临时原文件删除；

### 权限与业务

- 普通用户、机构账号、管理员分别进入正确工作台；
- 管理员不能访问健康内容；
- 机构账号只能访问绑定机构；
- 同行安排的参与者校验、容量扣减、日期冲突和取消释放正常；满额候补、空位事件与 outbox 可追踪且不重复；
- 报告复核发布时再次校验受检者和完整性，并与预约履约、事件、通知和锁档同步完成；
- 套餐申请、管理员审批及新版本生效正常，历史预约继续读取原版本快照；
- 提交后的报告保持永久归档，机构端没有撤下接口，用户时间线、趋势和 AI 持续读取；
- 关联账号切换记录 actor/subject/链，撤销或安全版本变化立即失效；健康页面只读当前有效账号；
- 健康码预约匹配只返回脱敏摘要，原始健康身份码不进入日志、URL、缓存或模型；
- AI 和报告识别服务密钥只来自服务器环境文件。

## 4. 发布流程

在项目根目录执行普通代码发布：

```powershell
.\scripts\deploy-server.ps1
```

发布脚本会执行后端依赖检查/测试、前端依赖审计/测试和生产构建，打包不含 `.env`、SQLite、普通上传文件、`项目文档` 和本地虚拟环境的发布包，通过 SSH 上传并创建时间戳版本。远端在停止写服务前，为新 release 独立创建 `venv`、安装并执行 `pip check`，保存排序后的 `DEPENDENCIES.txt` 和 `REQUIREMENTS.sha256`；当前 release 的解释器在此期间不变，依赖安装失败不会污染回滚运行时。随后脚本显式同步批准的公共 RAG 语料，并在 API、通知 worker、timer 和按开关启用的 MCP 都健康后完成切换。通知 worker 虽可在候选阶段启动并报告 active，但会停在关闭的文件门闩后，直到唯一公开提交点才允许领取或发送 Outbox。远程来源短暂超时时，只能使用 SHA-256 与清单完全一致的既有批准缓存；首次同步没有合格缓存时仍会失败回滚。因此《验收账号与预置数据》保留在本地和 GitHub，不进入服务器运行目录；显式媒体刷新会另行上传经校验的报告媒体包，完成后删除临时文件。

仅在已单独完成全部测试且保留验证记录时才可使用：

```powershell
.\scripts\deploy-server.ps1 -SkipTests
```

普通发布只执行 schema v13 保留式增量迁移。`-SyncDemoMedia` 不导入本地数据库；只有带 `-SyncDemoDatabase` 的显式命令会覆盖验收数据库。本轮全量验收发布不使用 `-SyncMailSettings`，服务器 SMTP 与密钥保持原值。

### 5.1 冷备份、候选验证与通知门闩

进入维护模式前，脚本先记录 Apache、HealthDoc systemd unit 与 `/var/lib/healthdoc/notification-worker.enabled` 原状态，并归档当前 release。随后停止 Apache、API、通知 worker、MCP 和 Agent timer，确认写进程均已静默，再移除通知门闩；冷备前以单事务把旧进程中断遗留的 `sending` 行转回 `failed` 且立即可重试，使首次 v12 失败回滚到不懂租约的旧 worker 时也不会永久卡信。静默后冷备份 openGauss 与上传，并把 root-only 环境、Apache、unit 文件、enable/mask 状态和门闩 present/absent 标记纳入同一恢复集合。数据库、上传和 release 归档创建后立即验证 tar 可读，恢复前还会再次验证；回滚会先恢复门闩原状态，再按旧 active-state 启动通知服务。

候选 release 依次验证真实数据库 SQL、v13 迁移、API `release_commit/schema_version`、静态 `/release.json`、通知配置预检、可选 MCP 与 Apache 配置。`healthdoc-notifications.service` 此时使用 `--start-gate-file` 启动，只能输出等待状态，不能产生邮件副作用。全部候选门禁成功且 Apache 仍关闭时，脚本先记录唯一公开提交点；从此不再自动冷回滚。随后启动 Apache、确认公共入口 active，再创建门闩允许通知副作用，避免任何“公网已经确认写入、脚本仍回滚旧库”的时间窗口。远端返回后，本地脚本再次 fetch 并核验 `origin/main`，同时读取公开 `/api/health` 与 `/release.json` 的 SHA/schema；这些提交点后检查失败只报告漂移并要求重新发布，不触发数据回滚。

另需确认：

- 生产发布分支和提交已评审；
- `.env`、SQLite、数据库备份、上传文件、开发文档、真实报告和密钥未进入代码发布包；
- 预置 SQLite 只在全量同步模式临时上传，且远端导入完成后删除；
- 全量迁移脚本已通过临时目标库逐表行数、完整性、外键和双向引用冒烟；
- RAG 批准清单、黄金查询和服务器持久目录权限已验证；
- 回滚版本、数据库恢复点和上传目录快照可用；
- Apache、systemd 与容器磁盘空间充足；
- 运维人员已知停机窗口和验证清单。

## 9. 回滚原则

- 应用代码与数据库 schema 必须作为同一个发布单元考虑。
- 如果数据库迁移已经提交，不能只把代码 symlink 切回不兼容版本。
- 回滚前停止写入，恢复数据库备份、上传目录、环境、Apache、兼容代码版本及其 release 独立虚拟环境。
- 覆盖 systemd unit 前记录文件和 enable/mask 状态；失败回滚时先恢复原 unit、执行 `daemon-reload` 并恢复原启用状态，再启动旧服务。
- 任何失败都先保存日志和现场快照，再执行预演过的回滚步骤。
- 不在生产环境临时手工修改表来绕过迁移脚本。

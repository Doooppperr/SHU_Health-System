# 康康健健 HealthDoc：项目需求与技术方案

> 文档状态：第七轮优化后的当前技术基线。当前数据库为 schema v13，更新于 2026-08-04；旧轮次仍有效能力已融合到本方案。

schema v13 在 v12 业务基线上新增正式资金闭环：预约提交生成 15 分钟待付款订单，付款后平台托管；报告发布锁档七个自然日且无未结投诉时，按逐人订单明细扣除 2.5% 服务费并将 97.5% 计入机构余额；投诉与退款合并，结算后机构责任退款须在 72 小时内处理，逾期自动暂停运营并在清偿后恢复。

schema v10 阶段将产品闭环扩展为：健康身份码亲友授权与真实姓名展示、预约身高/体重采集和服务端预约资料副本、机构取消责任及替代分院、站内与邮件双通知、标准附件槽和批注、104 项成人指标与异常方向、管理员永久改密、平台数据优先的 AI、机构目录模糊搜索、趋势指标多选及 10/15/20 条服务端分页。仍有效的规则已融合到本文和数据库、AI/OCR、验收主题文档。

schema v12 曾统一访客目录、实名认证、关联账号、健康码预约、报告复核和平台治理；这些能力在 v13 中继续保留。完整权限矩阵、资金状态机和迁移门禁见《业务规则与验收契约》。

## 1. 项目定位

HealthDoc 是面向现实生活的个人健康与体检服务平台，不是把数据库表包装成增删改查页面。平台连接普通用户、体检机构与系统运营人员，围绕以下完整旅程设计：

1. 用户持续记录日常健康状态，并在同一时间线看到自主记录与正式体检结果；
2. 用户按服务能力、适用人群、健康领域和可约日期选择体检套餐，可为同行家人统一安排；
3. 机构从预约到检开始，完成报告录入、复核和归档；
4. 套餐以版本化服务产品管理，平台审核变更但不改写历史订单；
5. 亲友访问依赖明确授权，管理员治理平台但不读取个人健康正文；
6. AI 与报告识别仅提供辅助，不替代医疗判断和人工复核。

### 1.1 从 1.0 到 3.0 的产品演进

| 阶段 | 解决的核心问题 | 形成的能力 | 对当前版本的影响 |
|---|---|---|---|
| 1.0：基础业务闭环 | 让用户、机构和管理员能够在同一系统完成账号、机构浏览、预约和基础健康记录 | 建立三角色、基础预约、个人资料、机构资料和健康数据雏形 | 账号体系、角色入口和基础服务关系继续保留 |
| 2.0：健康档案与机构履约 | 把零散 CRUD 提升为“预约—到检—报告—归档”的可追踪流程 | 引入自主测量、健康时间线、趋势、机构报告草稿/锁定/归档、亲友只读授权和更清晰的角色权限 | 报告归档不可改写、最小授权和任务式机构工作台继续保留；亲友读取在 v12 收敛为受控账号切换 |
| 3.0：现实平台与分院协作 | 让产品更接近真实体检服务平台，而不是数据库管理界面 | 引入健康领域、套餐版本、多人预约、容量候补、可靠邮件、图文报告、机构主体/分院、跨院归档只读和平台化 UI | schema v8 是历史起点；能力经 v9—v12 迁移后继续保留在当前基线 |

版本号描述产品能力阶段，schema 版本描述数据库结构，两者不是一一对应关系。当前开发、测试和部署统一面向 schema v13；v7—v12 只作为迁移链和历史说明中的基线。

### 1.2 第七轮资金产品边界

- 平台不采集银行卡号；付款窗口只确认平台订单并生成正式付款凭证。
- 多人订单由付款人一次支付，总订单与逐人订单明细分离，支持逐人取消、投诉、结算和退款。
- 资金账本分为平台托管、平台服务费、机构可用余额，任何资金动作均由不可变交易和分录表达。
- 机构首页展示可用余额、累计到账、待结算和累计退款；管理员只能查看订单资金与治理信息，不能借财务权限读取健康报告正文。

## 2. 页面体系与角色

系统采用“公开门户 + 三角色工作台”。

| 角色 | 默认入口 | 核心任务 |
|---|---|---|
| 访客 | `/`、`/explore/institutions` | 浏览启用机构、分院、在售套餐、“加入我们”，登录后继续预约 |
| 普通用户 | `/dashboard` | 健康总览、快捷测量、时间线、趋势、体检安排、机构服务、亲友和健康 AI |
| 机构账号 | `/org/dashboard` | 预约到检、报告生产、机构资料、相册、套餐版本与审核申请 |
| 系统管理员 | `/admin/dashboard` | 分院与机构账号、身份修正、套餐、投诉、评论和账号状态治理 |

三类登录角色具有独立导航、路由和后端接口。机构账号不能切换到其他机构；管理员不拥有个人测量、报告正文或健康 AI 上下文权限。

## 3. 业务需求

### 3.1 健康总览与自主测量

- 总览展示健康摘要、领域状态、最近体检、近期自主记录和待办提醒。
- 日常测量不设独立导航板块；总览保留“记录测量”按钮，以抽屉/对话框完成录入和修改。
- 支持身高、体重、心率、体温、血氧、空腹血糖等开放指标，同一指标同日可记录多次。
- 旧 `/measurements` 地址兼容返回总览，避免书签失效。
- 姓名、性别、出生日期首次确认后用户不能自行修改；未完成时只允许只读和账号安全操作。管理员可修正这三项，但不能查看健康档案。

### 3.2 健康时间线与趋势

- 时间线统一承载体检记录和自主记录，可按 `all/exam/self` 筛选。
- 自主记录保留用户自己上传/录入的时间与来源；体检记录可展开结构化指标、文本结论和附件。
- 预约创建、取消、到检、报告归档等节点以业务事件呈现，不把内部状态码直接当作产品主界面。
- 时间线、体检数据和趋势始终读取当前有效账号；查看关联亲友前先建立受控切换会话，不保留旧成员选择器。
- 趋势单列当前范围内最近异常，可展开全部异常，并标明健康方向、偏高/偏低/阳性/异常、来源、参考范围及“最新已恢复正常”。
- 同日存在机构归档指标时优先使用机构值；机构未提供该项时采用当天最后一次自主测量。
- 有可靠上下限的指标统一显示简洁“参考范围”卡；描述性项目或无可靠范围项目不展示“描述性测量值”“暂无统一参考范围”等无操作价值的提示。

### 3.3 体检机构与套餐产品

- 平台区分机构主体和分院；用户按机构主体分组浏览，服务能力、地址交通、营业信息、相册、评价、套餐和预约入口均明确标注具体分院。
- 未登录访客使用独立脱敏只读接口，仅获得启用分院和已审核在售套餐；机构登录邮箱、内部容量和管理状态不公开。
- 机构目录提供 300 ms 防抖搜索，服务端按机构主体名、分院名、地区、地址和交通信息做不区分大小写的字面量模糊匹配；分院字段命中时只返回匹配分院，机构主体命中时保留其全部启用分院。
- 套餐具有稳定业务身份和多个版本；版本包含名称、说明、价格、适用人群、覆盖健康领域和生效状态。
- 普通用户看到当前可售版本及清晰的服务差异，不展示内部表 ID 或数据库式字段表格。
- 机构提交套餐新增、调整、下架和恢复申请；管理员通过后生效，驳回或撤回不影响当前版本。
- 历史预约始终保留下单时的套餐版本、名称和价格事实。

### 3.4 同行体检安排、容量与候补

- 用户按机构、套餐、适用人群、领域与可约日期选择服务。
- 一次安排最多包含五名参与者，来源固定为当前有效账号、已关联账号或一次性健康身份码参与人令牌。
- 健康码匹配只接受启用、已实名且开启代预约的普通用户；返回姓名、性别、出生年份、脱敏身份码及预约所需的最近身高体重，不返回联系方式、病史或其他历史健康明细。
- 代预约只在预约表单展示本人、有效授权亲友或身份码验证受检者的最近身高体重，不自动开放对方的完整健康数据、趋势、报告或影像查看权限。
- 服务端统一复核所有参与者的日期冲突、套餐适用性和机构名额；任一人不满足条件时整组不创建。
- 所有入口按上海时区只允许明天至第 30 天；日期满额可订阅空位提醒，候补转换时重新校验参与人授权和隐私开关。
- 通知采用可追踪、可重试且防重复的 outbox 投递机制。
- 用户预约历史支持全部、近一周、近一月、近半年和自定义日期范围；固定每页 10 组并显示当前页/总页数，筛选改变时回到第一页，取消后页码越界时自动回退到最后一个有效页。

### 3.5 机构履约与健康档案

- 机构工作台按“今日到检—草稿—待复核—已发布”组织任务。
- 受检者、机构、日期和套餐版本由预约带入，机构无需搜索用户健康档案。
- 报告可手工录入或使用识别导入；识别出的低置信度、冲突、无效数值、单位问题和未映射字段必须人工复核。
- 健康档案可包含标准数值指标、文本结论和附件，覆盖现实报告的不同内容形态。
- 上传确认必须记录上传医生并进入 `pending_review`；复核确认必须记录复核医生。发布与预约履约、事件、通知、锁档及临时文件清理同步完成，之后不可撤回或改写。
- 普通用户在健康时间线查看归档结果，趋势与健康 AI 使用同一份获授权事实。
- 机构账号绑定具体分院。本院可创建/编辑草稿、上传确认进入待复核并复核发布；同一机构主体的兄弟分院只可查看已发布报告及附件，草稿和待复核内容不共享，跨机构读取拒绝。
- 跨院详情和附件读取写入访问审计；预约、容量、候补、套餐、投诉、评价和分院运营明细始终按分院隔离。

### 3.6 亲友、评论与隐私

- 一方接受申请后形成双向关联账号；双方独立保存备注，并可从头像菜单切换为对方的当前有效账号。
- 服务端记录真实操作者、有效账号和完整关联链，最多连续三层并禁止重复/循环。撤权、停用或安全版本变化立即使下游会话失效。
- 健康码临时参与人不会建立关联关系，也不会授予健康数据访问权。
- 用户完成该机构体检并拥有已发布记录后才可评价；管理员隐藏评论必须填写原因，可附加 7/30 天或永久禁言，每次处罚只可申诉一次。

### 3.7 平台治理与账号生命周期

- 管理员总览只显示账号、角色、机构主体、分院、套餐审核、投诉和评论等非健康统计。
- 公共注册不接受机构角色；管理员创建分院时同步设置一个全局唯一用户名、初始密码和机构邮箱，一个分院只有一个有效机构账号。
- 凭据邮件发送失败不回滚账号，进入 Outbox 重试；明文凭据使用服务器密钥加密暂存并在发送成功后清除。
- 机构软停用；套餐状态通过审核变更；机构工作人员离职不删除历史归档。
- 机构自助注销前必须无未来预约、待上传/待复核报告、未解决投诉或其他未结任务；候补关闭并通知，历史业务保留，管理员可恢复。
- 删除普通用户需明确确认并按数据生命周期规则处理个人健康数据。

### 3.8 健康 AI

- 访客 AI 只做公开导览；机构账号和管理员不使用个人健康上下文。
- 普通系统问题不发送健康数据，但不会清除当前对话的档案焦点；档案可由用户手动选择或由确定性语义解析在授权范围内自动选择。
- 档案引用是对话级持续上下文，发送后不清空；“这个报告”“这个指标”等连续追问继承同一成员和锚点报告，用户可随时更换或清除。
- 可分析内容只能属于当前有效账号；关联亲友必须先切换账号。健康身份码和不必要个人资料不进入模型。
- 服务端计算排序、极值、异常、缺失、来源优先和变化，模型只解释确定性事实。
- 支持 SSE 增量、取消、失败保留和重试；AI 结合当前问题、系统机构数据和会话级档案上下文直接生成回答。
- 聊天与分析不写业务数据库；私人档案不进入公共知识向量库。

### 3.9 投诉闭环与机构经营画像

- 每个个人预约最多一条投诉；正文、机构回复、用户升级和管理员回复使用追加式消息与事件，不覆盖历史。
- 投诉按 `institution_pending → user_confirmation → platform_pending → platform_processing → resolved` 流转；用户提交后可随时升级，升级后机构停止处理，由平台接管并关闭。
- 机构首页可按当前分院/整个机构及 30 天、90 天、12 个月、全部筛选匿名聚合画像。性别、年龄按去重受检者，套餐热度按已完成体检次数。
- AI 画像只接收聚合统计和套餐目录；缓存按范围、摘要哈希保存 24 小时，数据变化即失效，并始终展示样本数和小样本审慎提示。

## 4. 技术方案

| 层级 | 选型 |
|---|---|
| 前端 | Vue 3、Vite 6、Vue Router、Pinia、Element Plus、Axios、ECharts 6 |
| 后端 | Flask 3、Flask-SQLAlchemy、Flask-JWT-Extended、Flask-Cors、bcrypt |
| 本地数据库 | SQLite schema v12，`PRAGMA user_version` 管理结构版本 |
| 生产数据库 | openGauss，显式迁移、备份与逐表校验 |
| 文件 | 机构图片、经授权访问的报告附件；识别临时文件按生命周期清理 |
| 报告识别 | 本地 Mock 或华为云 OCR，保守映射并要求人工复核 |
| AI/RAG | SSE、批准的公共知识、本地向量检索与确定性健康事实 |
| 测试 | Pytest、Vitest、Vue Test Utils、jsdom、Vite production build |

健康总览、时间线、趋势和机构任务看板由后端提供权限专用 DTO；前端不拼接跨权限数据，也不复用管理员完整对象。

## 5. 数据与权限原则

- 每次请求实时校验角色、账号启用状态、实名认证、机构绑定及关联会话链。
- 自主测量与机构归档独立建模，但在健康时间线形成统一用户视图。
- “体检数据”只列机构归档报告；个人测量继续进入健康总览、健康时间线和健康趋势。
- “体检数据”日期筛选提供全部记录、近一周、近一个月、近半年和自定义范围；自定义起止日期不限制为相邻月份，可跨月、跨年查询，切换条件后从第一页重新加载。
- “健康趋势”使用相同的日期预设和跨年自定义范围；日期变化后重新查询当前有效账号、方向、来源和已选指标，并让 AI 图表解读使用完全相同的日期条件。
- 报告以源分院为所有者，兄弟分院获得归档只读能力但不复制数据；所有运营实体仍以分院外键隔离。
- 套餐身份与版本分离；预约和报告保留发生时快照。
- 同行安排、容量扣减、报告归档与套餐版本生效使用事务保证一致性。
- 文件访问通过业务权限验证，不公开整个上传目录。
- 管理员、机构、当前有效账号、健康码预约人使用不同 DTO，遵循最小字段原则。
- 健康身份码、报告正文、测量值和个人资料不进入公开日志。

## 6. 数据库升级与验收数据

目标结构为 SQLite schema v13。检查和升级命令：

```powershell
Set-Location .\backend
.\.venv\Scripts\python.exe .\scripts\upgrade_local_database.py --check-only
.\.venv\Scripts\python.exe .\scripts\upgrade_local_database.py
```

需要保留原测试账号、覆盖旧业务记录并生成 3.0 综合场景时：

```powershell
.\.venv\Scripts\python.exe .\scripts\reset_v13_demo_data.py --check-only
.\.venv\Scripts\python.exe .\scripts\reset_v13_demo_data.py --apply --yes
.\.venv\Scripts\python.exe .\scripts\validate_v13_demo.py `
  --database .\instance\health_system.db --upload-dir .\uploads
```

重置脚本只用于本地预置业务库；若存在非验收个人或机构账号会拒绝执行。生产 openGauss 必须先备份，再进行显式结构迁移与逐表核对，不能使用验收数据重置脚本。

## 7. UI 与非功能需求

- 三角色工作台支持桌面和移动端，具备加载、空状态、错误、403 和 404 页面。
- AI 入口位于顶栏；桌面打开侧栏时主内容按剩余宽度重排，不整体缩放页面。
- 窄屏 AI 使用焦点可达的遮罩层；关怀模式放大字体与关键控件，同时保持导航、卡片和表单不重叠。
- 表格仅用于真正需要精确比较的管理场景；普通用户页面优先使用摘要、卡片、步骤和时间线。
- 登录密码只保存哈希；机构初始凭据的待发送明文只以服务器密钥加密暂存，发送后清除。真实密钥来自被 Git 忽略的环境文件。
- 本地支持 Windows PowerShell，不要求额外数据库服务。
- schema、模型、接口、前端、测试和文档同步更新。

## 8. 当前实现与验收结论

- schema v12 代码契约覆盖访客目录、单机构账号、实名认证、关联账号、三类预约参与人、异常提示、报告复核、投诉、评论治理和机构画像；详细状态机与权限矩阵以《业务规则与验收契约》为准。
- 验收快照固定为 23 个启用可登录账号：2 个管理员、15 个单分院机构账号和 `test1`—`test6` 六个普通用户；旧重复机构账号仅停用并解绑，不计入可登录矩阵。
- `test6` 保持未实名认证且无健康业务数据；其余用户覆盖健康码开关关闭、身高体重两项/一项/均缺、三层关联链、混合预约、令牌失效、报告三态、投诉五态及评论处罚/申诉。
- 自动化数量、SQLite/openGauss 演练、构建、最终 Git SHA 与服务器冒烟结果只在真实执行后写入《测试报告》和《服务器部署与同步》，不得沿用 schema v11 数字冒充当前结论。

## 11. 6.0 Agent 需求增量

普通用户可以用自然语言提出“分析档案、解释趋势、比较机构/套餐、查询或办理预约、转人工”的目标。系统由 DeepSeek 选择类型化工具，所有事实来自获授权工具；确定性程序负责计算和写入。预约、整组取消、候补和人工工单必须生成可核对草稿并由用户逐次确认，重复提交不得产生重复副作用。

外部 Agent 通过 OAuth 2.1 风格的 Authorization Code + PKCE 和 MCP Streamable HTTP 接入；动态客户端注册必须管理员审批，scope、audience、Origin 和 redirect URI 每次校验。当前接口、数据和安全边界以《AI 与 OCR 开发说明》及《数据库设计说明》为准。
